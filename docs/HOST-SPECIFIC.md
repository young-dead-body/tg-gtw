# Что было привязано к исходному хосту

Для публичного снимка убраны локальный `docker-compose.override.yml`, скрипты `scripts/deploy-prod.sh`, `scripts/check-env-drift.sh`, `scripts/renew-web-tgk-cert.sh`, конфиги `infra/frp/` и внутренние документы о stage, сети и аудите. Эти файлы описывали конкретные машины и не нужны для общего развёртывания. Локальные `.env`, ключи TLS, базы и журналы в снимок не включены.

Оставшиеся особенности архитектуры, которые стоит учитывать при адаптации:

- `docker-compose.yml` и `docker-compose.vps.yml` предполагают два варианта запуска: на домашнем сервере за NAT и на VPS. Отдельные имена образов `telegram-gateway-prod-*` и `telegram-gateway-vps-*` появились из необходимости держать оба контура на одной машине деплоя.
- `MIGRATE_EXPECT_DB` сверяет имя БД с ожидаемым перед миграцией. Это защита от случайного обновления другой базы при переключении контуров; при другой схеме имён значение нужно задать в окружении.
- `scripts/vps/` и `infra/vps/` рассчитаны на Linux VPS с root/sudo, Docker, системным nginx, certbot и при необходимости frp. Порты `16443`, `21001–21005`, `13478`, `18090` и адрес подсети Xray `172.31.250.0/24` фиксированы в примерах и могут конфликтовать с сервисами другого хоста.
- Локальный `Makefile` всё ещё содержит команды для внутреннего CA (`make ca`, `make cert`) и ручных миграций. Для публичного VPS с Let's Encrypt внутренний CA не нужен.
- Прежняя схема DC-моста через пять портов и поддоменов сохранилась в коде и части конфигурации ради совместимости. Текущий путь Telegram WebSocket — `/tg/_gw/dc/<id>/apiws` на основном домене; для нового запуска отдельные DC-поддомены не требуются.
- `SOCKS5_ADDR` и опциональный Xray отражают сетевой маршрут исходного развёртывания. Если Telegram доступен напрямую, эти настройки можно оставить пустыми.

Шаблоны `.env.example` и `.env.vps.example` содержат только значения-примеры. Для реального запуска замените пароли, токены, адреса и домен своими значениями.
