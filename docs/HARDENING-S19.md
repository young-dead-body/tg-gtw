# Обновление S19

## Изменения доступа

DC WebSocket использует основной origin `/tg/_gw/dc/<1..5>/apiws`.
Браузер отправляет ту же host-only HttpOnly cookie, что и для `/tg/`.
Шлюз проверяет аккаунт, срок доступа, текущую версию согласия и ревизию
пароля. Разрешены только пять фиксированных Telegram DC и путь `/apiws`.
Проверяется Origin с сохранением HTTPS-порта; cookie/Authorization/CSRF
не уходят к Telegram. Лимит: 16 DC-соединений на аккаунт, 256 на процесс.

Каждые 5 секунд соединение повторно проверяется (таймаут проверки 3 секунды).
Блокировка, истечение доступа, отзыв сессии, смена пароля/версии согласия
закрывают действующие DC-соединения. При недоступности хранилищ доступ
закрывается. Аккаунты с истёкшим доступом также теряют admin API.

Raw-TCP passthrough/DC listeners больше не стартуют. Новая установка
требует DNS и сертификат только для основного домена. При прямом выходе
встроенный TURN-релей выключен; ограничения звонков описаны в
[инструкции развёртывания](deploy/README.md).

Шлюз переписывает поддерживаемую форму worker-бандла в same-origin URL,
включая запуск worker через blob. Неизвестный/слишком большой/неподходяще
сжатый worker не выдаётся. CSP запрещает прямые WebSocket/DC-запросы к
Telegram. Несовместимое обновление Telegram требует адаптации рерайта;
оно диагностируется метрикой и stage smoke-тестом.

## Порядок обновления

1. Создайте резервную копию БД и проверьте восстановление в изолированном
   окружении. Примените миграции 13–14 до старта новых API и proxy.
2. Обновите API, proxy, frontend и nginx согласованно через
   `sudo ./scripts/install.sh` на VPS. Порядок описан в
   [инструкции развёртывания](deploy/README.md).
3. Закройте старые DC-порты и проверьте, что DC-поддомены отвечают 410.
   В стандартных Compose их публикация удалена.
4. **Все прежние Redis-сессии без credential revision потребуют повторного
   входа.** На активной вкладке также может потребоваться перезагрузка.
5. Серверный cache key изменён; nginx-кэш executable assets отключён.
   Уже сохранённые браузером/Telegram ServiceWorker старые бандлы сервер
   удалить не может: при старых DC URL очистите данные сайта/Cache Storage
   и unregister ServiceWorker для шлюза, затем войдите заново. Это может
   потребовать повторного входа в Telegram.
6. Проверьте stage-сценарий входа, QR, сообщения, медиа и звонки, отзыв
   сессии и блокировку пользователя. После этого переносите релиз в прод.

Пароли и Telegram-идентичности не мигрируют автоматически из username.
Откат приложения требует согласованного восстановления прежней схемы
транспорта и версии миграций; частичный откат одного сервиса не поддерживается.

## Бот и восстановление пароля

Администратор в «Пользователи → Привязать Telegram» получает код для
сотрудника. Самостоятельная привязка доступна в `/?account=1` после входа.
Код действует 15 минут; новый код отменяет прежний. Передавайте его лично.

Сотрудник отправляет боту **в личном чате** `/link <код>`. В БД сохраняется
постоянный Telegram user ID. Username остаётся информационным полем.
Уведомления отправляются только по подтверждённому ID, поэтому старый
Redis username→chat registry больше не используется.

`/credentials` выдаёт ссылку `https://<gateway>/#reset=<случайный токен>`.
Она действует 15 минут и применяется один раз; новая ссылка заменяет старую.
В БД хранится SHA-256 токена. При открытии frontend убирает фрагмент из URL;
пароль меняется только POST-запросом с CSRF. Пароль не отправляется в чат.
Смена пароля или перепривязка Telegram аннулирует прежние reset-ссылки.
Выдача ссылки блокирует строку текущей привязки, исключая гонку со сменой ID.

Обновление хеша, времени ротации, истории и аннулирование ссылок атомарны
на уровне PostgreSQL. Отзыв сессий выполняется до изменения пароля; если
Redis недоступен, пароль/ссылка не изменяются. Дополнительно каждая сессия
привязана к версии пароля в БД: старые сессии не восстанавливают доступ при
гонке login/reset или после сбоя Redis.

## Личный кабинет и согласия

`/?account=1` показывает состояние шлюза и сессии, позволяет завершить одну
или все сессии и получить код привязки. Идентификаторы управления сессиями
являются SHA-256 от bearer-токенов; сами cookie-токены API не раскрывает.
После завершения текущей/всех сессий требуется вход заново.

Анонимное согласие привязывается через случайную HttpOnly cookie-квитанцию,
действующую до суток. Совпадение IP/User-Agent больше не означает совпадение
пользователя. Проверяется только текущая `consent.document_version`.
Старая версия при POST отклоняется с 409. Публикация новой версии документа
требует обновления текстов в `docs/152-fz` и `api/documents` в одном релизе;
CI проверяет совпадение копий. Изменять настройку версии следует после
публикации соответствующего текста. Тексты доступны из окна согласия.

## Ограничение памяти

Argon2id использует 64 MiB. На один API-процесс допускается одно вычисление,
не более 32 ожидающих запросов и ожидание до 2 секунд. Перегрузка возвращает
503 с Retry-After. Лимит общий для Hash/Verify всех экземпляров hasher.
Для большего потока авторизаций масштабируйте API с общей БД/Redis.
Это ограничение не ограничивает количество уже авторизованных пользователей.

## Бэкапы и сигналы

Дамп записывается в приватный временный файл, проверяется на непустое
содержимое и публикуется атомарным rename после fsync. Права файла 0600.
Ошибка не публикует частичный `.sql` и не удаляет старые копии. Пароль
PostgreSQL исключён из аргументов pg_dump. Используется клиент PostgreSQL17.

После успешного сохранения пишется `.last-success`; он восстанавливает
backup-метрику после рестарта. При подключении собственного Prometheus
можно использовать правила `infra/prometheus/alerts.yml`. Стандартный
Compose не запускает Prometheus или Alertmanager.

Штатная установка хранит SQL-дампы на VPS. Выгружайте их отдельно и
периодически проверяйте восстановление на изолированной машине. Команды
сохранения и восстановления приведены в
[инструкции развёртывания](deploy/README.md).

## Проверки

```bash
cd api && go build ./... && go vet ./... && go test ./...
cd ../bot && go build ./... && go vet ./... && go test ./...
cd ../web && npm ci && npm run lint && npm run typecheck && npm test && npm run build
npx playwright install --with-deps chromium
npm run test:e2e
```

PostgreSQL integration-тесты требуют `TEST_DATABASE_URL` **отдельной тестовой
БД**: тесты выполняют migrations down/up и удаляют тестовую схему.
Browser-тесты по умолчанию проверяют frontend на изолированных API fixtures.
Настоящий QR проверяется только по явно заданным `E2E_BASE_URL`, `E2E_EMAIL`,
`E2E_PASSWORD` от отдельного stage user-аккаунта (не admin):

```bash
E2E_BASE_URL=https://stage.example.com E2E_EMAIL=stage-user@example.com E2E_PASSWORD='...' npm run test:e2e
```

Для live QR нужен поддерживаемый Telegram Web K. Тест QR пропускается без
явного stage-конфига; fixtures не считаются доказательством живого QR-входа.
